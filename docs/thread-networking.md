# Thread implementation and validation

Use ESPHome 2026.10.2 pinned in requirements, ESP32-C6 with ESP-IDF, IPv6 enabled, device_type MTD and poll_period 5s. Do not assume SED polling puts the CPU to sleep. Conservative power model assumes active processor continuously; actual whole-node current must be measured.

Provision the existing HA Thread operational dataset locally in ignored firmware/tank_1/secrets.yaml and firmware/tank_2/secrets.yaml. Never publish it. 3.3 V UART initial flash on the custom board; HA ESPHome integration uses native API encryption. Ensure IPv6 path from HA through border router. Neither tank is a router, so place a mains-powered Thread router if site coverage requires one. One tank failing must not break the other's radio path.

Maintenance button sets poll period to 0 for ten minutes, allowing OTA; firmware restores 5s afterward. First validate this on a current-limited bench supply. Dataset recovery after cold boot, parent router replacement, border-router restart, IPv6 outage and OTA interruption are hardware acceptance tests, not simulated passes.

Fallback gate: if measured energy or 72 h connectivity soak fails, first evaluate ESP-IDF light sleep SED. Wi-Fi deep sleep at five-minute intervals is second preference and requires reliable AP coverage. Do not switch protocols merely because older ESPHome documentation lacked SED.

## Existing Raspberry Pi / Sonoff installation

Owner equipment: Raspberry Pi Zero2W, PoE HAT and Sonoff Dongle-LMG21 family USB radio already in Thread mode. Keep this existing border router; do not reset its dataset or flash Zigbee firmware. The [SONOFF introduction](https://dongle.sonoff.tech/guide/dongle-lmg21/dongle-lmg21-introduction/) identifies EFR32MG21; [SONOFF support](https://dongle.sonoff.tech/support/dongle-lmg21/) is the model-specific reference if recovery is ever needed. Current firmware, serial speed/flow control and service/container configuration must be read from the actual working installation, not guessed from ZBDongle-E instructions.

On the Pi, use the existing OTBR installation's `ot-ctl state` and `ot-ctl ifconfig` read-only checks (through its existing container if applicable). A functioning border router should have an attached Thread role and enabled interface. Check its existing infrastructure link and IPv6 forwarding using local diagnostics; a PoE HAT can provide a different interface from onboard Wi-Fi, so do not assume `eth0` or recreate network settings. OpenThread's [native setup](https://openthread.io/guides/border-router/build-native) and [Docker setup](https://openthread.io/guides/border-router/build-docker) explain that infrastructure-interface selection. These documents are references, not instructions to reinstall an already working router.

Retrieve the existing active operational dataset **locally** using the existing border-router/HA credential-management method and place its hex TLV in each ignored device secrets file. Do not paste the dataset, keys or private addresses into GitHub or this chat. Both nodes join the same existing network with independent ESPHome API keys/OTA passwords and device names. Use the native ESPHome integration over IPv6; these sensors are not Matter accessories and do not need Matter commissioning codes.

After owner-local flashing, verify each node independently attaches, appears through encrypted API and reports parent RSSI/link quality. Test one node powered off while the other continues, Pi restart, radio reconnect, infrastructure outage, parent change and serial/OTA recovery. The two MTD nodes do not provide a Thread router path for each other. If coverage near the steel tanks is poor, measure first and add a mains-powered router/relocate the border radio as needed. Existing Pi/radio compatibility and performance have not been tested remotely.
